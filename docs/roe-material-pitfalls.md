# ROE Blender 材质兼容避坑手册

本页记录 Rise of Eros 模型在 Blender 3.6 → XPS 转换中已经实际踩过并验证过的坑。
目标不是为每个角色不断增加宽泛特例，而是保留原始 FBX 语义、缩小修复范围，并用已知
角色做回归。插件使用说明见 [xps-addon.md](xps-addon.md)，需要人工覆盖时见
[roe-manual-material-repair.md](roe-manual-material-repair.md)。

## 先做这五项检查

1. 完全重启 Blender，确认 ROE XPS Tools 版本。覆盖插件文件不会刷新已经加载到内存的
   Python 模块；“磁盘是新版、界面仍跑旧版”会造成假复现。
2. 确认模型来源是保留完整材质槽的 FBX。AssetStudio 遇到同名对象会生成 `(1)` 目录，
   无后缀副本不一定更正确；应比较对象、材质槽和每槽面数。
3. 贴图目录优先选择 `D:\roe_exports\<角色>\_textures\`，并确认当前体型的 face、iris、
   eyebrow、hair 与 body Albedo 都存在。
4. 只有一个区域异常时使用“修复脸部 / 修复身体 / 修复翅膀”；首次导入或多个区域同时
   异常时才使用完整的“检查并准备材质”。
5. 验证最终 XPS，而不只看 FBX 场景：导出 `.mesh` 后在全新 Blender 场景重导入，检查
   mesh 面数、实际加载的 PNG 和 render group。

## 已确认的坑

### 1. 插件覆盖后没有重启 Blender

- **现象**：代码文件版本正确，但按钮、日志或转换结果仍像旧版。
- **根因**：Blender 继续使用内存里已加载的插件模块。
- **正确处理**：彻底退出并重新启动 Blender，再确认插件版本。
- **不要做**：不要因为热加载失败就修改 UV、材质槽或重复安装多个同名插件副本。

### 2. 同名 FBX 的 `(1)` 不是“旧副本”

- **现象**：身体只剩一个材质槽、腿部和衣服共用错误图集，或者 e06 导入后结构不完整。
- **根因**：AssetStudio 用 `(1)` 防止同名根对象互相覆盖；无后缀目录有时是材质分区不完整
  的副本。
- **已知案例**：a07 与 e06 应使用文档指定的 `(1)` HD FBX。
- **正确处理**：比较每个候选 FBX 的 mesh、材质槽名和每槽面数，选择结构完整者。
- **不要做**：不要只按目录排序选择第一份，也不要用一张 body 图强行覆盖全部槽。

### 3. 重新提取角色会清空角色输出目录

- **现象**：以前导出的 XPS 重导入后全黑或提示贴图 missing。
- **根因**：提取脚本会重建 `D:\roe_exports\<角色>\`，放在里面的 `.mesh` 和配套 PNG
  被一起删除。
- **正确处理**：把最终产物放到角色目录之外，例如
  `D:\roe_exports\xps_export\<角色>\`，并让 `.mesh` 与 PNG 保持同目录。

### 4. 原始材质分区比当前生成材质更重要

- **现象**：重复准备后身体多图集被压成一槽，或头部区域无法可靠重新分类。
- **根因**：生成后的材质名和面索引不能完整代表 FBX 原始槽语义。
- **正确处理**：保留对象属性 `roe_source_materials`、面属性
  `roe_source_material_index` 和来源 `roe_source_fbx`；旧场景缓存可疑时从原 FBX 按拓扑
  恢复。
- **兼容原则**：分区按钮只替换目标槽的材质，未选中的槽保留原材质对象和面索引。

### 5. F10 的 face 与 tears 跨同一个连通块

- **现象**：身体正常，但脸部大面积消失或透明。
- **根因**：F10 的同一连通块跨越 `pc_f_nk_face` 与 `pc_f_nk_tears` 材质边界。按整个
  连通块套用 Eyelid 权重和窄 UV 规则，会把 11,596 个脸面误判成透明罩层。
- **正确处理**：当 FBX 已提供独立 face 与眼部附属槽时，优先按每个面的原始材质索引
  保留 face/tears，再对语义不明确的面使用骨骼、UV 和几何兜底。
- **正确基线**：F10 `face/eye/lash/brow/overlay = 15354/864/900/228/390`。
- **旧错误基线**：`4148/864/900/228/11596`，看到这个结果说明仍在运行旧分类逻辑。
- **操作**：已有 F10 场景直接点“修复脸部”，无需重新处理身体。

### 6. 眼睛上像“眼镜片”的东西通常是 tears 覆盖层

- **现象**：眼睛附近出现半透明片、黑片或单眼“镜片”。
- **根因**：`pc_*_nk_tears` 是下眼睑泪光/动态阴影覆盖层，不是独立眼镜模型；权重和
  透明分类错误时会变成可见片状几何。
- **已知案例**：b02 的 tears 同时出现在 head 与身体网格；G09 的 tears 位于下眼睑。
- **正确处理**：tears 使用纯 Transparent，并在 ROE XPS 导出时跳过；不要删除网格。
- **判断实体眼镜**：必须能找到独立 glasses/lens 对象或材质槽；只有 tears 时不能当成
  眼镜材质修复。

### 7. 眼球在 Blender 与 XPS 使用的材质形态不同

- **现象**：FBX 场景眼睛正常，但 XPS 里白眼、整颗棕色或贴图缺失。
- **根因**：Blender 预览使用“眼白 + 圆形虹膜”的程序化节点，XPS 不支持该节点树。
- **正确处理**：导出前生成 `roe_eye_baked.png`，XPS 的 `5_eye` 必须引用这张烘焙图。
- **验证**：在全新场景重导 `.mesh`；不要只根据原 FBX 材质节点判断成功。

### 8. g09 的 wings 与 wings2 前缀会互相误匹配

- **现象**：主翼使用了零散羽毛片图集，纹理明显错位。
- **根因**：宽泛的 `wings*Albedo*` 同时命中 `wings` 与 `wings2`，字典序可能先选
  `wings2`。
- **正确处理**：先匹配完整 `_rgbx_Albedo` 文件干，再使用历史宽泛回退。
- **正确映射**：`wings → pc_g09_hd_wings_rgbx_Albedo.png`，
  `wings2 → pc_g09_hd_wings2_rgbx_Albedo.png`。

### 9. g09 翅膀与身体共用一个 mesh，但透明规则不同

- **现象**：翅膀黑底、硬边、实心卡片或黑色散点；也可能身体/衣服变半透明。
- **根因**：旧 XPS 路径把所有 ROE body 槽统一设为 RG5；反过来把整个 body 设 RG7 又会
  破坏不透明衣装。Blender 3.6 的 Alpha Hashed 在重叠羽毛片上还会出现噪点。
- **正确处理**：仅 G09 明确的 wing 槽在 Blender 用 Alpha Clip、XPS 用 RG7；同 mesh
  上的 body/skin 继续 RG5。
- **正确基线**：G09 render group 为 `body/skin/wings2/wings = 5/5/7/7`。
- **兼容边界**：其他旧角色即使有 alpha wing 名称，也不自动改变历史 XPS render group。

### 10. 身体按钮与翅膀按钮必须做到槽级隔离

- **现象**：只想修衣服，却把刚修好的翅膀覆盖；或修翅膀时身体材质重新生成。
- **根因**：身体和翅膀可能是同一个 Blender 对象，按对象而不是按原始槽处理会互相影响。
- **正确处理**：“修复身体”排除 `wing/wings[数字]` 槽；“修复翅膀”只包含这些槽。
- **无翅膀角色**：按钮应提示没有识别到翅膀并做到零修改；F10 是回归样本。

### 11. e06 FBX 缺少一个 Blender 3.6 预期的 bind setup

- **现象**：导入报 `KeyError: Root`，场景留下 4 个无材质网格和未完成骨架。
- **根因**：`wp_e_06` 已归入 Root 骨架，但 FBX 蒙皮簇缺少该网格的
  `armature_setup`。异常后的对象只是半成品。
- **正确处理**：仅在 setup 缺失时用网格世界矩阵和骨架 bind matrix 补齐；绝不覆盖
  已有绑定，导入结束后恢复 Blender 原 FBX 方法。删除旧半成品后重新导入完整 `(1)` FBX。
- **不要做**：不要在异常留下的半成品上继续准备材质，也不要永久修改 Blender 安装目录
  的 FBX 导入器。

### 12. Albedo 命名并不完全统一

- **已知差异**：g02 把 `Albedo` 拼为 `Abedo`；g07 的 PNG 省略槽名中的 `_hd_/_ld_`；
  多图集 body/skin 需要从原始槽名推导 body1/body2。
- **正确处理**：优先标准、完整、角色精确名称；只有未命中时才按明确的历史别名回退。
- **不要做**：不要让全目录第一个 `*Albedo*` 成为所有槽的默认答案。

### 13. i03/i04 没有独立的高清 iris/eyebrow Albedo

- **现象**：i03/i04 的身体和头发可见，但点击完整准备或“修复脸部”后 face 仍没有贴图；
  日志同时报告缺少 `eye_iris` 与 `eyebrow`。
- **根因**：旧流程要求 face、iris、eyebrow 三项全部存在才开始设置 head。i 体型实际只
  提供 `pc_i_ld_eyes`，眉毛与眼线已经烘进 face Albedo，没有独立 eyebrow Albedo。
- **角色差异**：i03 没有角色专属 face，使用 `pc_i_nk_face`；i04 必须优先使用
  `pc_i04_hd_face`，否则会丢失角色专属的白色眉毛外观。hair 使用同样的专属优先规则。
- **正确处理**：仅在标准 `eye_iris` 未命中且体型明确为 i 时回退 `pc_i_ld_eyes`；仅 i
  体型允许 eyebrow 图缺失，把没有贴图的 stroke 几何保持透明并在 XPS 导出时跳过。
- **正确基线**：i03 `face/eye/lash/overlay = 11616/864/636/3284`，face 图为
  `pc_i_nk_face_rgbx_Albedo.png`；i04 为 `12172/864/636/3284`，face 图为
  `pc_i04_hd_face_rgbx_Albedo.png`。两者 XPS 只导出 `5_face` 与 `5_eye` 头部可见分区，
  不生成无贴图的 `7_lash` 占位网格。
- **兼容边界**：其他体型仍优先并要求其正常的高清 iris/eyebrow 资源，不能把 i 体型的
  降级策略全局应用。

### 14. 残缺的原始材质表比没有材质表更糟（f05 "没有脸"）

- **现象**：f05 的 `pc_f05_hd` 与 `pc_f05_outfit1_hd` 导出后完全没有脸——只有一对眼球
  悬在头发里，下半张脸是一片空白。身体、头发、眼球、睫毛都正常。
- **检查结果全绿**：插件自检报 `缺贴图 0`，manifest 里 `untexturedSlots`、
  `familyMismatches` 全空，face 槽甚至正确挂上了 `pc_f_nk_face_rgbx_Albedo.png`。
  **贴图没问题，是那个槽一个面都没有。**
- **根因**：这两份 FBX 的 head 只保留了 `pc_f_nk_eyebrow` 和 `pc_f_nk_tears` 两个原始
  材质槽，face 和 eyes 槽在打包时就没了，整张脸的多边形挂在这两个残存索引上。
  `classify_head` 见到有原始槽名就信任它：`source_is_tear` 把 11,172 个面判给透明罩层，
  `source_is_brow_or_lash` 把另外 8,376 个面判给睫毛和眉毛，face 槽剩 **0 个面**。
- **对照**：同角色的 `pc_f05_hd`／`pc_f05_hd (1)` 根本没有原始槽名（`src=[]`），走几何
  回退反而分对了（face 18,322 面）。**所以"有一份残缺的表"比"完全没有表"更有害。**
- **正确处理**：`classify_head` 开头判断——原始槽里有 eye/brow/lash/tear 这类特征槽、
  却**没有任何 face 槽**时，判定这份表不可信，清空 names 与 indices 走几何回退。
  修复后 f05 两个模型 face 槽都恢复到 18,322 面。
- **不要做**：不要因为这个改选另一份 FBX——f05 的 `(2)` 才有正确的三槽身体分区
  （`(1)` 只有一个身体槽，还会按通配符错挂成 outfit1 的贴图）；也不要去删罩层几何。
- **兼容边界**：守卫只在"有特征槽 + 无 face 槽"时触发。a06/a07/a08/b02/f06/f10/g09/
  i03/j01/m02 十个角色改前改后逐槽面数**完全一致**，5 个合成回归测试全过。
- **新增护栏**：`export_character_model_blender.py` 现在统计 head 每个槽的面数并输出
  `headFacePolygons`，为 0 时批量脚本会红字报警——这个坑当初就是因为所有检查都只看
  "贴图有没有挂上"、没人看"槽里有没有面"才漏过去的。

### 15. 没有独立 eyes 槽的头，眼球会被"显式 face 槽"规则抢走（g05 白眼）

- **现象**：g05 双眼是两片空白，没有虹膜。脸、睫毛、眉毛、身体都正常。
- **检查结果同样全绿**：`缺贴图 0`，`pc_g_nk_eye_iris_rgbx_Albedo.png` 也确实挂在
  eye 槽上——**只是那个槽 0 个面**，眼球几何被并进了 face（14,633 = 13,769 + 864）。
- **根因**：眼球的连通块识别其实完全正常（428 面、Eyeball 权重 0.998、UV 铺满 0–1，
  `w['eyeball'] > 0.9` 直接命中，`cls[r] = 1`）。问题出在最后那轮**逐面覆盖**：
  g05 的原始槽是 `['pc_g_nk_face', 'pc_g_nk_eyebrow', 'pc_g_nk_tears']`，**没有
  `pc_g_nk_eyes`**，眼球面挂在 face 材质索引上，于是为 F10 加的
  "显式 face 槽 → 强制 slot 0" 规则把已经判对的眼球又拽回了脸。
- **对照**：同体型的 g01/g04/g06 都有独立 `pc_g_nk_eyes` 槽，eye 槽正常 864 面。
- **正确处理**：该覆盖增加 `and slot != 1` 例外——组件级判定为眼球时不被拉回 face。
  "~100% Eyeball 权重 + 完整 0–1 虹膜 UV" 比"共用同一个材质索引"是更强的证据。
  修复后 g05 恢复 `face/eye = 13769/864`，与 g01/g04/g06 一致。
- **兼容边界**：F10 那条规则本来是把误判进罩层(4)的脸救回来，例外只放行眼球(1)，
  F10 基线不变。十个敏感角色改前改后逐槽面数完全一致，5 个合成测试全过。

### 16. 头身合一且没有 Eyeball 骨骼组的模型，眼球完全不被处理（a00 碎块眼）

- **现象**：a00 通用素体的双眼是一团白褐色碎块——不是"平淡"，是明显的贴图错采样。
- **根因链**：a00 的网格叫 `pc_a00_nk`（**不是** `*_nk_body`），顶点组只有 `Bip000 *`
  骨骼、**没有 `Eyeball` 组**，名字里也没有 `head` 词元。于是
  `find_head()` 两条判据（Eyeball 顶点组 / 名字含 head）全部落空返回 `None`，
  整个眼/睫/眉分类被跳过；裸模 worker 的 `split_combined_nude_body` 又因为名字不匹配
  `(?:^|_)nk_body$` 而直接 `return None`。**两条路都没接住它**，
  README §4 里"a00 两网格/两材质"就是这个状态的历史记录。
- **眼球其实是标准的**：网格里有两个 **432 面、UV 铺满 0–1**（0.0004–0.9995）的组件，
  和 g06 等角色的眼球签名完全一致，只是拿到了身体图集——满 0–1 的 UV 去采样身体图，
  自然渲成碎块。
- **正确处理**：`export_character_model_blender.py` 在 `find_head()` 返回 `None` 时，
  用几何特征（250–800 面 + UV 基本铺满 0–1）直接认出眼球组件，追加一个
  `module.eye_mat()` 程序化眼球材质（眼白 + 中心圆盘虹膜）。a00 命中 864 面
  （2×432），manifest 记 `fusedHeadEyes`。
- **不要做**：不要为此放宽 `find_head()`——把整块身体当 head 交给 `classify_head`，
  会把大半个躯干判成脸，那正是 `split_combined_nude_body` 当初要解决的问题。
- **兼容边界**：只在完全找不到独立 head 网格时触发。120 个模型里只有 a00 属于这种。

### 17. 打包贴图时不能遍历 `bpy.data.images`

- **现象**：清掉 `FBX_GameObjects` 子目录里的冗余贴图副本后，两条批量管线全部报
  `贴图打包失败: ... 无法打包文件,找不到资源路径 '...\FBX_GameObjects\...\xxx.png'`。
- **根因**：FBX 导入器会**按 FBX 同级目录**为文件里提到的每张贴图创建图片数据块；
  插件随后用 `_textures`（或暂存目录）里的副本**另建**一套数据块来做材质。两套并存，
  只有后者被材质引用。`pack_images()` 遍历 `bpy.data.images` 全打包，就会连那批
  **没有任何材质使用**的导入残留一起打包。
- **两个后果**：平时"成功"但把无用贴图嵌进 .blend（g11 的 blend 因此虚胖一倍，
  66.8 MB → 修复后 31.8 MB）；源文件一旦被清理就直接硬失败。
- **正确处理**：沿模型材质的节点树收集 `TEX_IMAGE` 节点的 image，只打包这些。
- **不要做**：不要为了让打包通过而保留那些冗余副本——它们确实是冗余的，
  该修的是打包逻辑。

### 关于 head 槽为 0 的判读

`headSlots` 里某个槽是 0 **不一定是缺陷**，判读规则：

| 槽 | 为 0 时 |
|---|---|
| `face` | **永远是缺陷**（坑 #14） |
| `eye` | **永远是缺陷**（坑 #15） |
| `brow` | i 体型正常（眉毛烘进 face 图，见坑 #13）；k06 刘海遮眉也正常 |
| `lash` | 眼部被遮挡的角色正常（f11 戴金色面罩） |

批量脚本只对 `face` 与 `eye` 报警，其余留在 `headSlots` 里供人工判读。

## 每次修改材质逻辑后的最低回归矩阵

| 样本 | 必须保持的结果 |
|---|---|
| F10 | 五槽 `15354/864/900/228/390`；单独修脸不改身体；XPS `5_face` 使用 face Albedo |

## 新问题的排查顺序

1. 保存原始截图、角色 ID、FBX 路径、贴图目录和插件版本。
2. 在全新 Blender 3.6 场景导入，记录每个 mesh 的原始槽名、每槽面数、UV 范围和实际
   顶点组权重；不要先运行修复按钮。
3. 运行对应的单区按钮，比较非目标区域的材质对象引用与面索引，必须完全不变。
4. 记录准备后的五槽/多槽面数和每槽实际图片路径。
5. 导出 XPS，在全新场景重导，记录 mesh 名、面数、图片和 RG。
6. 修复条件优先使用“角色 + 对象 + 原始槽”的窄语义；不得把某个角色的 alpha、绑定或
   几何阈值全局扩散到其他角色。
7. 添加最小合成回归测试，再用出现问题的实际角色做集成测试；两者都通过后才更新已安装
   插件和版本号。

## 禁止用来“碰运气”的处理

- 不要删除疑似 tears、角膜或眼部覆盖层几何来掩盖分类问题。
- 不要修改 UV、骨骼权重或合并材质槽，除非已经证明原始 FBX 数据本身损坏。
- 不要把所有透明材质统一设为 RG7，也不要把所有 body 槽统一设为 RG5。
- 不要用宽泛文件名前缀覆盖明确的完整贴图文件干。
- 不要在没有验证非目标槽引用不变的情况下声称“单独修复”。
- 不要只看 Blender 材质预览；必须验证 XPS 重导入结果。
